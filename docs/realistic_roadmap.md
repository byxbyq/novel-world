# 小说世界引擎 — 现实可执行开发计划

> 制定日期：2026-07-17
> 基础：两份代码级验证报告（`goal_system_critical_analysis.md` + `deep_critique_verification.md`）
> 约束条件：个人开发者、AI 辅助开发、业余时间投入

---

## 一、现实约束分析

### 1.1 时间与精力瓶颈

作为个人开发者，实际情况：

| 维度 | 现实 |
|------|------|
| 每日可用时间 | 2-4 小时（业余时间） |
| 每周有效时间 | 15-25 小时 |
| 可维持高强度周期 | 2-3 个月后需要缓冲 |
| 可同时推进的并行线 | 最多 2 条（一条主攻 + 一条轻量修补） |
| 可承受的架构震荡 | 低——不能推倒重来，必须增量改造 |

结论：原计划的 12 个月 4 阶段对个人来说过于乐观。实际能推进的深度开发的周期约 **6-8 个月**，之后进入维护和按需迭代。

### 1.2 AI 辅助的优势和局限

**AI 擅长的（应该委派给 AI，不要自己手写）：**

| 任务类型 | 示例 | 原因 |
|----------|------|------|
| 批量代码生成 | Prompt 模板抽离、配置文件改造、序列化/反序列化 | 模式固定、量大、人工写容易漏 |
| 单元测试编写 | 对已有函数写测试用例 | AI 能覆盖边界条件 |
| 代码翻译/迁移 | backend Goal → novel_world Goal 字段平移 | 机械化翻译，AI 不出错 |
| 文档生成 | 从代码注释生成 API 文档 | 节省大量时间 |

**AI 不擅长的（必须亲自动手确认）：**

| 任务类型 | 示例 | 原因 |
|----------|------|------|
| 架构决策 | Tick 循环重排、引擎统一方案 | AI 不理解全局耦合关系 |
| 数据模型设计 | Goal 的 weight 字段如何与调度器交互 | AI 容易制造不一致 |
| 跨文件重构 | 两个引擎数据模型对齐 | 涉及多处修改，AI 容易遗漏 |
| 性能敏感代码 | 碰撞引擎关键路径 | AI 不知道瓶颈在哪 |

### 1.3 原规划中哪些是"过度设计"

以下原规划项对个人开发者来说是过度设计，建议砍掉或无限期推迟：

| 原规划项 | 判定 | 理由 |
|----------|------|------|
| 多租户架构 | 🔴 砍掉 | 没有 B 端客户，不需要 |
| 容器化部署（Docker/K8s） | 🔴 砍掉 | pyinstaller 打包 exe 完全够用 |
| CI/CD 流水线 | 🔴 砍掉 | GitHub Actions 个人用够用，不需要 Jenkins |
| 商业化订阅系统 | 🔴 砍掉 | 先有用户再说 |
| B 端 API 开放平台 | 🔴 砍掉 | 没有企业客户 |
| 移动端 APP | 🔴 砍掉 | 桌面版先跑通 |
| 云端版（SaaS） | 🔴 砍掉 | 运维成本个人扛不住 |
| 模板市场 | 🔴 砍掉 | 没有用户基础，模板没人买 |
| 多媒介导出（EPUB/有声书） | 🟡 推迟 | 先把小说生成质量做好 |
| 自动化测试全覆盖 | 🟡 推迟 | 核心路径手动测试 + AI 写关键测试即可 |
| Prompt 热重载/版本回滚 | 🟡 推迟 | 先集中管理，版本控制用 Git |
| 实时协作编辑 | 🟡 推迟 | 个人开发不需要 |

## 二、修改后的阶段划分

### 阶段 1：核心重构——先止血（第 1-3 个月）

**目标**：修 P0 致命问题，打通双引擎，能稳定出一章像样的小说，剧情不再随机发散。

#### 1.1 P0 致命修复（必须做，第 1-6 周）

| 序号 | 任务 | 来源 | 预估工时 | AI 可用性 | 说明 |
|------|------|------|----------|-----------|------|
| P0-1 | **Tick 循环重排：移除随机游走优先逻辑** | 批判一 1.1 | 1 周 | ❌ 需亲自设计 | 将 `_random_move_characters()` 从 tick() 第一步移到最后，或改为仅当角色无目标时才随机移动。目标驱动行为必须优先于随机移动。这是最致命的架构缺陷——不修这个，之后所有目标体系改造都是白做。 |
| P0-2 | **引擎统一：双引擎数据模型对齐** | 批判三 3.3 | 2 周 | ⚠️ 半自动 | backend 的 Goal（有 weight/priority）和 novel_world 的 Goal（纯字符串）必须统一为一个数据模型。方案：以 backend 的 Goal dataclass 为准，novel_world 的 Character.goal 字段升级为 Goal 对象列表。对齐后删除重复代码。 |
| P0-3 | **Adapter 适配层：打通 backend ↔ novel_world/engine** | 批判一 1.1 | 1 周 | ⚠️ 半自动 | 目前两个引擎的 tick() 和 advance_tick() 是两套独立链路。构建一个 Adapter 层，让 NovelEngine.advance_tick() 成为唯一的对外入口，backend 的旧代码通过 Adapter 调用新引擎。 |
| P0-4 | **CollisionEngine 改造：长期目标对立 → 碰撞第一权重** | 批判一 1.2 | 1 周 | ❌ 需亲自设计 | 当前碰撞类型优先级：`priority_map = {"目标对冲": 3, ...}`——目标对冲竟然不是最高优先级。修改为：如果双方长期目标存在对立（不止是关键词匹配，还要检测语义层级），自动提升碰撞烈度至最高。同时，碰撞引擎读入角色的 Goal.weight 来加权。 |
| P0-5 | **HardConstraintController 泛化** | 批判二 2.2 | 1 周 | ⚠️ 半自动 | 当前 914 行硬编码为「陈阳×苏晚」恋爱故事。将硬编码的角色名/主线阶段/配角名提取为配置项，从 WorldConfig 读取。这是"改一行配置就能适配不同故事"的基础设施。 |
| P0-6 | **EngineConfig 落地（max_chapters + 终局行为）** | 批判一 3 | 3 天 | ✅ AI 可主导 | backend/engine_config.py 已有字段定义，只需接入 NovelEngine.advance_tick() 流程：检测 `current_chapter >= total_chapters` → 触发 `finalize_story()`。 |

**P0 交付物**：引擎不再无限循环，角色行为由目标驱动（而非随机游走），碰撞逻辑以目标对立为首要因子，换了世界设定后约束器不再失效。

#### 1.2 P1 核心补齐（第 7-12 周）

| 序号 | 任务 | 来源 | 预估工时 | AI 可用性 | 说明 |
|------|------|------|----------|-----------|------|
| P1-1 | **Goal 增加 weight 字段 + 调度排序** | 批判一 2 | 2 天 | ✅ AI 可主导 | novel_world 引擎统一数据模型后，在 Goal 中增加 weight 字段（backend 已有），在 `tick_advance()` 中按 weight 降序处理目标。默认权重：主角=3.0，重要配角=1.5，龙套=0.5。 |
| P1-2 | **WorldConfig.main_objective 接入引擎** | 批判一 1 | 3 天 | ⚠️ 半自动 | WorldConfig 已有 `main_objective` 字段，但只在 backend prompt 中使用。接入 NovelEngine：初始化时读取 main_objective，调用 `align_goals_to_main_objective()` 调整角色目标权重，将主线注入 `generate_world_event()` 的 AI prompt。 |
| P1-3 | **本章收尾 prompt 优化** | 批判四 4.1 | 2 天 | ✅ AI 可主导 | 当前 `finalize_chapter()` 只是简单聚合叙事文本后截断。优化 prompt 模板：要求 AI 必须收束本章至少 1 条角色目标线、不得在悬念处粗暴截断、给出下章伏笔（1-2 句）。 |
| P1-4 | **Prompt 抽离到注册表（集中管理版）** | 批判二 2.2 | 3 天 | ✅ AI 可主导 | 将散落在 ai_client.py、collision.py、narrative.py 等文件中的 prompt 模板集中到一个 `prompts/` 目录或 JSON/YAML 文件。先不做热重载和版本回滚——目标是集中管理而非运行时动态切换。修改 prompt 时只需要改一个文件。 |
| P1-5 | **AI prompt 中明确注入世界规则作为行为约束** | 批判三 3.1 | 1 天 | ✅ AI 可主导 | 当前 WorldConfig.rules 只是拼接成文本注入 prompt，AI 可能忽略。优化为结构化约束格式（如"你必须遵守以下规则，违反将导致生成作废：..."），并在 prompt 末尾重复强调。 |

**阶段 1 交付物**：
- **Beta 桌面版**（pyinstaller 打包 .exe）
- 能跑通完整一章，剧情不再完全随机发散
- 角色行为由目标驱动（而非随机移动）
- 引擎有明确的停止条件和终局行为
- 换世界设定后不出现硬编码角色名

### 阶段 2：补齐核心功能（第 4-6 个月）

**目标**：DM 模式可操作 + 时间线检查可用 + 天意指引形成 V1.0。

| 序号 | 任务 | 优先级 | 预估工时 | AI 可用性 | 说明 |
|------|------|--------|----------|-----------|------|
| 2-1 | **DM 状态机 + WebSocket + 暂停/继续/单步** | P0 | 2 周 | ❌ 需亲自设计 | 实现 DM v2 文档 §3.1-3.2 的基础设施。前后端 WebSocket 通信，引擎支持 PAUSED/RUNNING/STEP 三种状态，DM 面板可暂停引擎。这是 DM 模式的地基，必须先做。 |
| 2-2 | **DM 干预核心 API：修改角色目标/属性/位置** | P1 | 2 周 | ⚠️ 半自动 | 实现 DM v2 文档 §3.5 中最核心的干预类型：Modify Character（目标增删改、属性修改、位置传送）。这是 DM 最常用的操作，先不做 Force Action 和 Adjust World。 |
| 2-3 | **DM 干预：注入事件** | P1 | 1 周 | ⚠️ 半自动 | 实现 DM v2 文档 §3.5.1 的 Inject Event 能力。DM 可以手动触发一个事件（如"天降陨石"），并指定 `affect_goals=True` 让角色目标随之调整。 |
| 2-4 | **天意指引（复用 DM 管线）** | P1 | 1 周 | ⚠️ 半自动 | 天意指引本质上是"自动化的 DM 干预"——引擎在每章开始或关键节点，根据世界主线目标自动生成"天道意志"约束，注入 AI prompt。复用 DM 的干预管线，增加一个 `DivineGuidanceGenerator` 自动触发。 |
| 2-5 | **TimelineChecker — Fast 规则检查** | P1 | 2 周 | ⚠️ 半自动 | 先实现 Fast 规则（硬性逻辑检查，不依赖 AI）：角色行踪连续性、时间倒流检测、章节间因果关系断裂。Deep 规则（需要 AI 深度分析）和 AI 规则（需要 AI 理解语义）后补。 |
| 2-6 | **Faction 势力目标** | P1 | 1 周 | ✅ AI 可主导 | 在 Faction 数据结构中增加 `goals: List[Goal]` 字段，复用 Goal 层级体系。实现 `align_faction_goals()` 方法（代码已有骨架），根据主线目标为势力生成贴合的目标，并级联下发到势力成员的角色目标。 |
| 2-7 | **前端 DM 面板 + 时间线面板** | P1 | 2 周 | ⚠️ 半自动 | 在现有前端基础上增加 DM 控制面板（暂停/继续/单步 + 干预表单）和时间线面板（显示 TimelineChecker 检查结果）。不用重写前端，增量添加。 |
| 2-8 | **章节数量设定 + 自动收尾** | P1 | 1 周 | ✅ AI 可主导 | 基于阶段 1 的 EngineConfig，前端增加「总章节数」「终局行为」配置入口。优化 `finalize_story()` 方法：不只是一次 AI prompt 调用，而是遍历所有角色的 ULTIMATE 目标状态，逐一生成结局段落，最后聚合为尾声章节。 |
| 2-9 | **地域-资源-角色目标联动（基础版）** | P2 | 1 周 | ⚠️ 半自动 | 实现最小可行的联动：角色有目标 → 解析目标中的地点关键词 → 向目标地点移动（替代随机移动）。不要求路径规划和 A* 寻路——先做到"角色向目标方向移动"而非"随机乱逛"。 |
| 2-10 | **PromptRegistry 完整版（版本/热重载）** | P2 | 1 周 | ✅ AI 可主导 | 在阶段 1 集中管理的基础上，增加版本标记和热重载能力。修改 prompt 文件后无需重启引擎即可生效。Git 做版本回溯即可，不需要自建回滚系统。 |
| 2-11 | **前端批量编辑（角色/势力批量）** | P2 | 1 周 | ✅ AI 可主导 | 增加批量导入（CSV/JSON）、批量目标编辑（如"所有反派增加一个目标"）、势力资源批量配置。 |

**阶段 2 交付物**：V1.0 桌面版。DM 可在运行中暂停、干预角色目标和属性、注入事件；TimelineChecker 可检测时间线断裂；天意指引自动约束剧情走向；角色不再完全随机移动，而是向目标方向移动。

## 四、AI 辅助开发建议

### 4.1 任务分工策略

**适合派给 AI 一次性完成（你只需审查结果）：**

| 任务 | 为什么适合 AI | 操作方式 |
|------|--------------|----------|
| Prompt 模板抽离 | 纯文本搬运，从 .py 搬到 .yaml，不会出错 | 告诉 AI 所有 prompt 所在的文件和行号，让它生成 YAML 文件 + 修改导入代码 |
| Goal 数据模型字段平移 | backend Goal → novel_world Goal，机械映射 | 给出字段对照表，AI 批量替换 |
| 配置类改造（EngineConfig 接入） | 已有的 dataclass 接入已有的循环，纯管道连接 | 告诉 AI "在 advance_tick() 的第 N 步之后插入检查逻辑" |
| 前端批量编辑面板 | HTML + JS，模式固定 | 给 AI 现有前端代码，让它仿照现有角色卡片生成批量编辑界面 |
| WorldRuleGuard 规则解析 | 关键字匹配逻辑，AI 擅长写 | 告诉 AI "把 rules 列表中的每条规则解析为正则或关键词列表" |

**需要你亲自设计确认后再动手（不要让 AI 直接写）：**

| 任务 | 为什么不能直接交给 AI | 建议流程 |
|------|----------------------|----------|
| Tick 循环重排 | 涉及整个引擎的执行流，AI 不知道全局耦合关系 | 1. 自己画出新的 Tick 流程图 2. 和 AI 讨论每个步骤的边界条件 3. 让 AI 生成代码 4. 逐行审查 |
| 引擎统一方案 | 两个引擎有数十处不一致，AI 容易遗漏 | 1. 自己列出 backend Goal 和 novel_world Goal 的字段对照表 2. 确定"以谁为准"的策略 3. 让 AI 逐文件改造 |
| CollisionEngine 目标对立 → 烈度映射 | 涉及碰撞语义理解，AI 可能给出不合理的权重分配 | 1. 自己定义"目标对立程度 → 碰撞烈度"的映射表 2. 让 AI 实现映射逻辑 |
| DM 状态机设计 | 暂停/恢复/单步涉及并发和状态一致性 | 1. 自己定义状态转移图 2. 和 AI 讨论边界 case 3. 让 AI 实现 4. 亲自测试 |
| Adapter 层设计 | 需要理解两套代码的调用链路 | 1. 自己画出调用链路图 2. 确定 Adapter 的接口签名 3. 让 AI 填充实现 |

### 4.2 单人开发节奏建议

**三步节奏**（每个子任务）：

```
第 1 天（30min-1h）：设计确认
  - 明确这个任务要改哪些文件
  - 明确输入/输出/边界条件
  - 写一个简短的「任务卡片」（不需要正式文档，几行字即可）

第 2-4 天（每 2-3h）：实现
  - 核心逻辑亲自写或逐行审查 AI 生成的代码
  - 改动涉及 >3 个文件时，先做最小可行改动验证

第 5 天（30min）：验收
  - 跑一遍完整流程（初始化 → 生成一章 → 检查输出质量）
  - 确认没有引入新 bug
  - Git commit + 标注完成
```

**每周节奏**：

| 时间段 | 做什么 | 原因 |
|--------|--------|------|
| 周一-周三 | 核心任务（P0/P1 修复） | 精力最好的时候做最难的事 |
| 周四-周五 | 辅助任务（Prompt 优化、前端补齐） | 可以交给 AI 主导，自己审查 |
| 周末 | 验收 + 文档更新 + 规划下周 | 保持全局视角，不陷入细节 |

**不要做的事**：

- ❌ 不要同时开 3 条以上的开发线——个人精力不够，会导致每条线都做不完
- ❌ 不要在工作日晚上做大架构改动——容易出错，留到周末上午做
- ❌ 不要在没跑通上一章之前就开始下一章的优化——稳扎稳打
- ❌ 不要追求"一次完美"——先出能跑的版本，再迭代。Perfection is the enemy of done.
